# Отчёт по резервному копированию баз данных

## Задание 1. Резервное копирование (Кейс финансовой компании)

### 1.1. Восстановление данных в полном объёме за предыдущий день

**Подходящий вариант:** полное резервное копирование (Full Backup) с ежедневным расписанием.

Полный бэкап создаёт копию всей базы данных на определённый момент времени. Если делать его ежедневно (например, ночью), то в случае сбоя можно восстановить состояние БД на конец предыдущего дня. Это самый простой и надёжный вариант с точки зрения восстановления — нужна только одна копия. Минус — большой объём и время создания, но для ежедневного цикла это приемлемо.

**Дополнительно:** можно сочетать с дифференциальным бэкапом (полный — раз в неделю, дифференциальный — ежедневно), чтобы сократить объём ежедневных копий, сохранив возможность восстановления за предыдущий день.

### 1.2. Восстановление данных за час до предполагаемой поломки

**Подходящий вариант:** непрерывное архивирование журналов транзакций (WAL / binlog) + периодический полный бэкап.

Такой подход называется **Point-in-Time Recovery (PITR)** — восстановление на момент времени. Полный бэкап даёт базовое состояние, а журналы (WAL в PostgreSQL, binary log в MySQL) содержат все изменения после него. При сбое база восстанавливается из полного бэкапа, а затем «докручивается» журналами до нужного момента — например, за час до поломки.

**Ключевое требование:** журналы должны непрерывно архивироваться на отдельный носитель. Без этого восстановление на произвольный момент времени невозможно.

### 1.3.* Моментальное переключение на работающую или починенную базу при поломке

**Да, такой кейс возможен** — это достигается с помощью репликации.

При репликации существует главный сервер (мастер) и одна или несколько копий (реплик/слейвов), которые получают изменения в реальном времени. Если мастер выходит из строя, система может автоматически или вручную переключиться на реплику. Это обеспечивает минимальное время простоя (низкий RTO).

**Важное ограничение:** репликация защищает от отказа оборудования, но **не заменяет резервное копирование**. Если на мастере случайно удалят данные, это удаление мгновенно попадёт на реплику. Поэтому репликация должна использоваться **вместе** с бэкапами.

## Задание 2. PostgreSQL

### 2.1. Пример команды резервирования и восстановления (pg_dump / pg_restore)

**Резервирование (создание дампа):**

```bash
# Логический дамп базы в архивном формате (custom)
pg_dump -U username -Fc -f backup.dump dbname
```

**Восстановление:**

```bash
# Восстановление из архива в базу данных
pg_restore -U username -d dbname backup.dump
```

**Пояснение:**

- `pg_dump` создаёт логическую копию базы данных — SQL-скрипт или архив, содержащий команды для пересоздания объектов и данных.
- Формат `-Fc` (custom) — наиболее гибкий: позволяет выборочно восстанавливать объекты и сжат по умолчанию.
- `pg_restore` используется для восстановления из архивных форматов (custom/tar), созданных `pg_dump`.

### 2.1.* Автоматизация процесса

**Да, процесс можно автоматизировать.**

Способы автоматизации:

1. **Планировщик задач (cron / Task Scheduler)** — регулярный запуск скрипта с `pg_dump` по расписанию.
2. **Скрипт-обёртка** — bash-скрипт, который делает дамп, сжимает его, копирует в удалённое хранилище и удаляет старые копии по политике хранения.
3. **Специализированные инструменты** — `pgBackRest`, `Barman` — предоставляют готовые механизмы расписания, проверки целостности, инкрементальных копий и ротации.

**Пример простого cron-задания (ежедневно в 2:00):**

```bash
0 2 * * * /usr/bin/pg_dump -U backup_user -Fc -f /backups/db_$(date +\%Y\%m\%d).dump dbname
```

## Задание 3. MySQL

### 3.1. Пример команды инкрементного резервного копирования

**Ключевой момент:** в MySQL инкрементное резервное копирование выполняется через **бинарный лог (binary log)**, а не через `mysqldump`.

**Порядок действий:**

1. **Включить бинарный лог** на сервере (параметр `log-bin`, включён по умолчанию в современных версиях).

2. **Создать полный бэкап** (базовую точку):

   ```bash
   mysqldump -u root -p --flush-logs --single-transaction dbname > full_backup.sql
   ```

   Флаг `--flush-logs` закрывает текущий бинарный лог и начинает новый — это фиксирует точку, с которой начинается инкремент.

3. **Инкрементное копирование** — скопировать файлы бинарных логов, созданные **после** полного бэкапа.

   Сначала посмотреть список логов:

   ```sql
   -- Просмотреть список бинарных логов
   SHOW BINARY LOGS;
   ```

   Затем скопировать нужные файлы:

   ```bash
   # Скопировать нужные файлы (например, начиная с того, что был создан после полного бэкапа)
   cp /var/lib/mysql/binlog.000002 /backup/incremental/
   ```

4. **Восстановление:** сначала применить полный дамп, затем «проиграть» бинарные логи:

   ```bash
   mysql -u root -p dbname < full_backup.sql
   mysqlbinlog /backup/incremental/binlog.000002 | mysql -u root -p dbname
   ```

**Альтернатива:** `MySQL Enterprise Backup` (`mysqlbackup`) поддерживает инкрементальные бэкапы через опцию `--incremental` с указанием базовой копии.

### 3.1.* Преимущества реплики по сравнению с обычным резервным копированием

Реплика даёт преимущество в следующих случаях:

| Ситуация | Преимущество реплики |
|---|---|
| **Отказ основного сервера** | Мгновенное переключение на реплику — минимальный простой (низкий RTO) |
| **Высокая нагрузка на чтение** | Реплику можно использовать для распределения read-запросов, снижая нагрузку на мастер |
| **Необходимость отчётов/аналитики** | Тяжёлые аналитические запросы выполняются на реплике, не мешая основной работе |
| **Плановое обслуживание мастера** | Реплика принимает нагрузку, пока мастер обновляется или обслуживается |

**Ограничение:** реплика **не защищает** от логических ошибок (ошибочное удаление, некорректный `UPDATE`) — они мгновенно реплицируются. Поэтому репликация **дополняет**, но не заменяет резервное копирование.
